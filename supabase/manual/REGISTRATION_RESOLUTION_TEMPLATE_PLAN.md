### 4.1 CI_MYANMAR (คงไว้ — จำกัดขอบเขต)

- **หมวด:** คง `ci` เหมือนเดิม
- **สถานะเนื้อหา:** คง PARTIAL/NEED_REVIEW — **ยังไม่กรอกเข้า CRM** จนกว่าจะมีแหล่ง "CI แท้"
- **ไม่** ผูก P09/P14 เป็นแหล่งหลักของ CI อีกต่อไป (ย้ายไปตระกูลใหม่)

### 4.2 ตระกูลใหม่ — "ขึ้นทะเบียนใหม่ / ขออนุญาตทำงานตามมติ ครม."
- **หลักการแกน:** **1 มติ ครม. ที่ตรวจแล้ว = 1 แม่แบบ** (ห้าม overload)
- **หมวด (แนะนำ):** เพิ่มค่าใหม่ `registration` *(หรือ `resolution` — เลือกได้ค่าเดียว ให้เจ้าของตัดสิน)*

## 5. Naming convention สำหรับ template code ในอนาคต

กติกาบังคับจากระบบ: `^[A-Z0-9_]{2,60}$` (ตัวพิมพ์ใหญ่ + ตัวเลข + `_` เท่านั้น, ยาว 2–60)

**รูปแบบที่แนะนำ (1 มติ = 1 code):**

```
REG_RESOLUTION_<YYYYMMDD>_<GROUP>
```

- `REG_RESOLUTION_` — prefix คงที่ บอกว่าเป็นงานขึ้นทะเบียน/ขออนุญาตตามมติ ครม.
- `<YYYYMMDD>` — **วันที่มติ ครม.** (เลขล้วน) — ใช้เป็นตัวแยกมติที่ชัดที่สุด
- `<GROUP>` — กลุ่มเป้าหมายแบบสั้น (เช่นสัญชาติ/สถานะ) เป็น ASCII UPPER

**กติกาย่อย:**
- ถ้ายังไม่ยืนยันวันที่มติ (เช่น P14) → **ยังไม่ตั้ง code** ห้ามใช้ `TODO`/วันที่เดา (คงไว้ในตระกูล CI/แผนจนกว่าจะได้วันที่จริง)
- หนึ่งมติที่มีหลายสาย (เช่น นายจ้างยื่น / บริษัทนำเข้ายื่น) ให้ **แยกสายด้วย form_refs ภายในแม่แบบเดียว** ก่อน — ยังไม่ต้องแตกเป็นหลาย code เว้นแต่เจ้าของยืนยันว่าเป็นคนละกระบวนการจริง

## 7. กติกาแกน: 1 มติ ครม. ที่ตรวจแล้ว = 1 แม่แบบ

- **ห้าม**สร้างแม่แบบมติ ครม. โดยไม่มี **PDF ของมตินั้นที่อ่าน text ได้และตรวจแล้ว**
- **ห้าม**รวมหลายมติเป็นแม่แบบเดียว แม้เนื้อหาจะดู "คล้ายกัน"
- **ห้าม**เดา/เติมรายละเอียดกฎหมายของมติใหม่โดยไม่มีแหล่งยืนยัน (ตามกติกาสเตจ)
- ถ้ามติหนึ่งถูกแทนที่ด้วยมติใหม่ → สร้างแม่แบบใหม่ (code วันที่ใหม่) และทำเครื่องหมายของเก่าเป็น superseded — **ไม่ทับของเดิม**
